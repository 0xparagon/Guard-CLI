## Summary

Makes the workspace's own targets compile and adds a registry-consistency test:

- **#612** the CLI binary's two compile errors (`no_clear`, 3-tuple pattern)
- **#611** the checks crate's duplicate `mod tests` (`E0428`)
- **#613** the 11 test call sites still destructuring the scan result as a 3-tuple
- **#609** a test that every registered check has docs, an all-findings trigger and a fixture pair

## Pre-existing breakage (not changed here)

`main` (b49b083) does not build the `checks` lib: `admin.rs`, `balance.rs`, `hardcoded_address.rs` and the three `unprotected_*` modules reference helpers and fields that don't exist (tracked in #570, #573, #574, #575; `hardcoded_address.rs` lost `function_spans` / `effective_lines` / `enclosing_function` in merge `935e236`). Those issues belong to other contributors, so this PR does **not** touch those files. To verify the changes below, a throwaway local-only commit repaired them (imports, restoring the three helpers from `65854de`, a `match` over `syn::UseTree`). That commit was then rebased away, and the diff against the tested branch equals exactly the reversed repair.

Until those issues land, CI on this branch fails in the `checks` lib exactly as it does on `main`.

## #612 cli: `no_clear` and the 4-tuple pattern

Done:
- `#[arg(long)] no_clear: bool` on `Commands::Scan` ("Don't clear the terminal between watch-mode re-scans"), bound in the handler, so `should_clear = !no_clear && ...` compiles
- `run_scan` matches `Ok((results, files_scanned, files_skipped, _check_panics))`
- README usage: `--watch` and `--watch --no-clear` example
- `cargo build --workspace` succeeds (with the local repair); `soroban-guard scan --help` lists `--no-clear`

Not done in this PR:
- What to do with check panics in `run_scan` (explicitly out of scope in the issue)

## #611 checks: `mod tests` defined twice

## #609 tests: registry-consistency test

Done:
- `crates/checks/tests/registry_consistency.rs` iterates `default_checks()` and requires for each check: a ``## `<name>` (Severity)`` heading in `docs/checks.md`, a `// Triggers` comment naming it in `examples/all-findings/src/lib.rs` (a comment may name several checks), and `test-contracts/<base>-vulnerable` + `-safe` from an explicit name to fixture map (`reinit`, `xc-input`, `nonce`, the original `vulnerable`/`safe` pair, ...)
- All problems are collected and reported together; a check missing from the map fails with a clear message, and a second test rejects map / allow-list entries for unregistered checks
- `TRIGGERS_ALLOW_LIST` with a reason per entry: `missing-event-emission` (fires on almost every state-mutating method in all-findings, 26 findings, so no single method is dedicated to it)
- The test found one real gap: `examples/all-findings` never triggered `panic-in-contract` (its storage `.unwrap()` is deliberately excluded). Added `fee_or_panic`, a plain `Option::unwrap()` with a `// Triggers` comment; a scan confirms it fires
- Both tests pass
